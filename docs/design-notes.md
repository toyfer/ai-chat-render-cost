# Design Notes: 引き算の表示制御エンジン（初期メモ）

最初にAIと壁打ちして作った設計案では「UIフレームワーク非依存のインクリメンタルMarkdownパーサーとブロックストア」を中心にしていましたが、以下の理由から方針を大きく組み直しました。

1. 単一メッセージ内のインクリメンタルMarkdown解析とブロック単位メモ化は、すでに [ai-markdown](https://github.com/ai-markdown/ai-markdown)、[vercel/streamdown](https://github.com/vercel/streamdown)、[Markstream](https://github.com/Simon-He95/markstream-vue)、[StreamMD](https://github.com/jvoltci/stream-md) などの先行プロジェクトが精力的に解決している。
2. 解決したい本質は「Markdownを速く飾ること」ではなく、**「電源に制約のあるモバイル環境で、対話の本質ではない描画仕事をどれだけ減らせるか」**である。

このメモでは、コードを書く前段階として「本当に意味のある制御層とは何か」を整理します。

## 基本方針：パーサーではなく「実行制御と縮退」を担う

自前でCommonMark準拠のパーサーを抱えると、リンク参照定義や脚注、Setext見出しといった「後ろの文脈で前の解釈が変わる構文」のエッジケース処理に開発コストを奪われます。そのため、パース処理そのものは既存の軽量パーサーやシンプルな構造分割に委ね、エンジン本体は**会話タイムライン全体のリソース管理とスケジューリング**に集中させます。

## 4つの設計アイデア

### 1. 最小テキストを標準（Default）に、Rich装飾をオプトインにする

従来のチャットUIは「常にフル装飾し、重くなったら軽量化する」設計になりがちですが、省電力エンジンでは逆を標準とします。

- **Default (Plain / Minimal)**: 段落、改行、見出しの視覚的区別、等幅の枠だけのコード領域のみを描画する。アニメーションや点滅カーソルは動かさない。
- **On-demand Rich**: ユーザーが「装飾を表示」ボタンを押したブロック、あるいは端末がAC電源接続中かつ画面内にあるブロックに限り、シンタックスハイライトやKaTeX・Mermaidを実行する。

### 2. 「50msごとの追従」ではなく「CPUを休ませるバッチ更新」

60fps（約16ms）や50ms間隔のタイマー更新は、文字が滑らかに見える一方で、モバイルCPUをアイドル状態に戻さず継続的に起こし続けます。

- エコモードでは、受信バッファへテキストを溜めつつ、画面反映を「250〜500msごと」または「空行（段落の切れ目）が来たタイミングごと」に間引く選択肢を提供する。
- Page Visibility API を監視し、タブやアプリが非表示になった瞬間に描画スケジュールを完全に停止し、復帰時に1回だけ最新状態へ同期する。

### 3. JS製仮想スクロールの前に、標準CSSスキップと「記憶の脱水」

JavaScriptで可変高さの仮想スクロールを自作すると、スクロールイベント監視や高さ計測のためのDOM参照がかえって負荷やレイアウトずれを招く場合があります。

- **描画のスキップ**: Web標準で広く利用可能になった `content-visibility: auto` と `contain-intrinsic-size` をまず活用し、画面外のレイアウトとペイント処理をブラウザ側の最適化に任せる（[web.dev 解説](https://web.dev/blog/css-content-visibility-baseline?hl=ja)）。
- **記憶の脱水（Dehydration）**: 画面から大きく離れた過去のメッセージについては、ハイライト用の大量の `<span>` 要素、SVG図表、パース済みASTオブジェクトをメモリとDOMから破棄し、生の文字列と推定高さだけを残した最小ノードへ縮退させる。

### 4. 単一メッセージではなく「会話タイムライン」のライフサイクル管理

ベンチマークでも問題になりやすいのは、1本の長い回答よりも「50往復・500往復と積み上がった会話履歴」です。コアのデータ構造は単発のドキュメントではなく、各メッセージが `streaming`（生成中）／`active`（可視範囲）／`dehydrated`（過去ログとして縮退済み）のどの状態にあるかを管理するモデルを前提とします。

## 未決事項・検証すべき前提

- そもそも現代のモバイルブラウザ（Safari / Chrome on Android）において、Markdownのパースコスト・DOMノード数・アニメーションのどれが消費電力に一番効いているのかは、実機計測データが集まってから優先順位を決める。
- 既存のチャットUI（Open WebUI等）のオプションや拡張機能として実装した方がユーザーに届くのか、独立した軽量ビューアやライブラリにすべきかも含めて開かれた課題とする。
